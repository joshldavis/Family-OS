# Household capture Storage erasure boundary

The shared made-again app uses a private `captures` Storage bucket. Its capture upload path is `<household-id>/<uuid>.jpg`; generated illustrations and step pictures can live in nested paths under the same household ID. `public.captures.storage_path` points to an object, but deleting the database row does not remove that object. The source inspected for these path shapes was `joshldavis/made-again` main at the time of this review. This is not a claim that the source exactly matches deployed production bytes.

`eraseHouseholdCaptureStorage` accepts an already authorized, server-side bucket client. It lists every object under the exact UUID prefix using Storage `listV2`, rejects any returned key outside that prefix, deletes in batches of at most 1,000 through the Storage API, then lists again to verify no objects remain. No route invokes it yet. The CI test uses synthetic files in a disposable local Supabase instance, including a nested illustration and a second household. It does not list or delete live objects.

Full household/account erasure still needs a durable, authorized server workflow: stop new uploads, delete Storage objects, verify the bucket is clear for that household, then remove database records and verify completion. Storage deletion is not part of the database transaction; failures need safe retry and an audit record. Shared caregivers and retained `public.illustration_requests` metadata need separate policy decisions before wiring this into the actual made-again app. Never run a migration or erasure against the shared project based on this test alone.
