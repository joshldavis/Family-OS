## State vocabulary and present boundary

- **Operational production:** only code already on `main` belongs here. The existing general Family OS app and Daily Agenda code are on main; this audit does not verify live runtime or database state. None of the Operating Modes, Learning Support, School Agent, or approval-ledger PRs below is merged into main.
- **Implemented and tested draft:** source exists on an open draft branch and its recorded branch-head CI succeeded. Stacked branches include their ancestors; their PR diffs are incremental.
- **Preview-only:** an isolated Learning Lab demo may display a flow. Synthetic, session-only approval receipts never authorize or create an assignment.
- **Unexecuted SQL/contract:** proposals or server interfaces exist, but no real Family OS migration or wired endpoint is established. Disposable PostgreSQL tests are evidence about the fixture only.

## Decisions and unresolved release gates

1. Keep one Family OS app. General Family remains the baseline; Learning Support and Custom are reversible modes. Hiding a module must not erase data. [Original roadmap](https://github.com/joshldavis/Family-OS/blob/main/ROADMAP.md) has older FOS-002/003/004 labels that describe broad phases; the later PR labels FOS-002/003/004/005 describe smaller School Agent milestones. Use PR/issue numbers to disambiguate.
2. Keep agents under parent control: Capture → Interpret → Review → Approve → Execute → Verify. The current lab reaches only an in-memory draft approval. No real mail/Classroom reader, classification service, durable approval, trusted assignment route, external message, or live Google Calendar sync is established.
3. Identify the actual Family OS Supabase project by nonsecret project ref and deployment environment. Connected account listings in [#17](https://github.com/joshldavis/Family-OS/pull/17) show other projects, not an identified Family OS project. Never infer identity from a project name or query unrelated databases. Confirm Preview/Production credentials are isolated; Vercel metadata shows service-role variable entries for both but does not prove separate values.
4. Reconcile the actual schema, backups and migration history with #2 and #5 in a disposable clone; replace permissive enrollment policies; verify Auth, household/child roles, RLS and direct Data API isolation. Implement bounded invitations and preserve existing users. Browser role and client filtering are not authorization.
5. Specify and test consent before any real school/child source capture: who grants/revokes it, source scope, retention, deletion/export and audit visibility. Keep provider and service-role secrets server-only. Avoid sensitive real child records in the Learning Lab.
6. Build the real adapter and endpoint for #16 only after those gates: exact bearer session, fresh parent membership, source revision, explicit field confirmation, unique family/source/action claim, one transaction for assignment and receipt, safe retry and rollback. Test against a verified disposable Supabase clone with real Auth/RLS and concurrent connections, then review opt-in rollout and observability. #17's synthetic PostgreSQL success does not satisfy this.
7. Complete manual desktop/mobile/accessibility QA in the isolated, access-protected Learning Lab; check feature flags and absence of persistence/network execution. Recorded PR descriptions give preview URLs, but this audit does not independently prove their current availability or contents. The conversation's [Learning Lab link](https://family-os-learning-4yoscn0w7-joshldavis-projects.vercel.app/#/) is a reported preview, not a production deployment verification.
8. Remaining broad roadmap items: child support data slice with scoped permissions, secure AI proxy/orchestrator, School/Learning/Advocacy agents, live Gmail/Canvas/Classroom/Calendar integrations, wellness review and external-pilot privacy/retention/metrics. These are planned, not delivered by the draft stack.

- The conversation called the School Agent “end-to-end” and the secure approval infrastructure “completed.” Precisely: #15 is an end-to-end **fictional UI rehearsal**; #16 is a tested **mock transaction contract**; #17 verifies **synthetic PostgreSQL ledger behavior**. None confirms an operational approval-to-assignment flow.
- The #15 PR description says a branch preview was requested and manual browser QA remained; the conversation says an updated preview was live. Preserve both claims, and recheck deployment metadata and browser behavior before treating the preview as accepted.
- #16's original “SQL not executed in PostgreSQL” limit was superseded only for the isolated fixture by #17. It remains unexecuted on the real Family OS database.
- The original ROADMAP checkboxes for FOS-001A/B/C predate these drafts. Draft implementation is not merged completion. Issue #14 and PR descriptions contain later progress; this index controls status wording until the roadmap is reconciled.
- Acceptance evidence still needed: actual project identity, schema/backup review, real RLS and invitation tests, consent/deletion policy, full transactional adapter, live-like replay/rollback, manual UX QA, deployment provenance, and a reviewed rollout decision.
